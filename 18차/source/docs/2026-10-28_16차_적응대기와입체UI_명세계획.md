## 제어 재현과 최소 수리 범위 보완

실제 검사에서 최종 대상 확인 이후 제스처를 보류하고 Settings 활성화를 확정한 뒤 해제하자 이전 좌표 제스처가 완료됐다. 화면 전환 확인 전에 snapshot을 반환한 원래 Safety 실패는 이와 구분하며, 이번 제어 RED를 제품 수리의 근거로 사용한다. prepare 및 잠깐의 제어창 대기 뒤 worker에서 대상을 다시 확인하고, 창 이벤트·일시정지 세대의 허가를 main 전달 직전에 비차단으로 재검사한다. main에서 창 조회를 기다리지 않는다. Android에는 앱 전환과 제스처 전달을 원자적으로 묶는 API가 없으므로 모든 물리적 경합 제거를 보증하지 않는다.

worker 초기화 전 실행→일시정지 순서를 제어한 검사에서 paused=true인데 pauseStartedAt이0으로 덮이고300ms 동안 활성시간이303ms 증가했다. 초기화·시작·정지·일시정지는 같은 모니터로 보호하고 현재 세대에서만 초기화하며 일시정지 시작 시각을 보존한다. 이전 실행의 deadline을 새 실행 초기화 검증에 사용하지 않는다. 즉시 정지한 큐 작업의 측정 재초기화 금지도 별도 검사한다. 기존 UI 실측 비교를 정지 후로 옮기거나 숫자 오차를 허용해 결함을 숨기지 않는다.

## 별도 저해상도 성능 실험

기본1080×2280/420dpi에서15차는210초,16차는125초 안에15회가 완료되지 않았다.16차는6회완료·12정상터치/12번누름·오터치0이며 OCR25회완료106.4초가 측정됐다. 이 부분 결과를15회완주 또는 실제 게임 정확도로 표현하지 않는다.

제품의 OCR 생략·축소·이미지 캐시는 추가하지 않는다. 별도 소유 기기540×1140/210dpi 환경에서15차와16차를 동일 fixture·폰트배율·CPU/RAM·모델 시작 조건으로 재비교할 수 있다. 실제 bitmap 크기와 글자 기하를 기록하며 em크기를 실제 글자 픽셀 높이라고 단정하지 않는다. 낮은 해상도의 성공으로1080의 실패를 대체하지 않고 환경 효과와 버전 효과를 구분한다. 기존52+12 회귀는 기본1080에서 유지한다. 최종 안전 수리 APK에서 다시 측정한다.

## 실제 저해상도 실패와 CPU 조건의 별도 비교

540×1140/210dpi·CPU2·RAM2048·swiftshader에서 실제 InputImage540×1140과 글자 최소ink26×28을 확인했다. 15차는210068ms에11회/23터치,16차는125091ms에7회/15터치로 각각 기한 실패했다. 부분 터치의 오터치0을15회 정확도로 확대하지 않는다. OCR 측정은 process 호출 전부터 main 완료 처리까지이며 순수 모델 추론 시간만으로 단정하지 않는다.

다른 판단의 읽기 검토 후 제품·검사·기한은 유지하고 소유 기기의 CPU만2에서4로 바꾼 별도 실험을 선택했다. RAM2048·swiftshader·540×1140/210dpi·폰트배율1.0·같은 APK·새설치 후 추가 워밍업0을 유지한다. 각 별도 비교는480초 공유 예산을 사용하며 기존125초 대기·120초 수락·15회·30터치·오터치0을 바꾸지 않는다. 구현자 첫 CPU4 관측은67087ms/15회/30터치/오터치0·실제OCR60회였다. 한 번의 관측을 CPU 증가의 보장 효과나 제품 자체 개선률로 표현하지 않는다. 같은 CPU4의15차 비교와 별도 verifier 재확인을 최종 결과에 구분한다.

실험 뒤 소유 기기는 원래CPU2·1080×2280/420dpi로 복원하여 기존 기능 회귀를 유지한다. 제품에는 새로운 OCR 생략·축소·이미지 캐시를 추가하지 않았다.
